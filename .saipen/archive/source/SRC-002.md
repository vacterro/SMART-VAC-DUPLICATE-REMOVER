[P0] [CORE-001] delete_duplicates_gui.py:DuplicateFinderApp.delete_selected / DuplicateEngine.verify_record — final destructive authorization is still check-then-delete on a mutable pathname

EVIDENCE:
- delete_duplicates_gui.py:199-226 verifies rec.path by lstat/stat/hash and then returns a Boolean authorization detached from the filesystem object that was verified.
- delete_duplicates_gui.py:874-912 describes verification as "final destructive authorization", but the actual sequence is verify_record(rec) at 887, survivor verification at 896-906, followed later by path-based send_to_trash(rec.path) at 912.
- send_to_trash itself accepts only a pathname, so the verified object is not bound to the object subsequently removed/recycled.
- Existing regression test_delete_duplicates.py:683-695 mutates the selected file BEFORE the final verify_record call. It proves the old confirmation-window TOCTOU was narrowed, but does not cover mutation after verify_record returns and before pathname deletion.
- Deterministic audit probe injected replacement immediately after the selected record's second/current-boundary verify_record returned True. The selected path was overwritten with unique unscanned bytes before delete_selected resumed. Current code then removed that replacement and reported:
  selected_verify_calls=2
  replacement_exists=False
  original_exists=True
  status="✅ Удалено файлов: 1"
- Equivalent desired-property audit regression failed:
  AssertionError: False is not true : an unscanned replacement appearing after final verify must survive

DEFECT:
CORE-002's stale-path protection is still a classic TOCTOU at the actual destructive boundary. The code verifies one filesystem object and later asks the OS to delete whatever object currently occupies the same pathname. A sync client, editor, rename/replace operation, or other concurrent actor can therefore install an unscanned file after verification and have this application recycle/delete that replacement. This is direct unintended data loss and invalidates the stated invariant that files changed/replaced since scanning are never deleted.

REPAIR:
- Replace the Boolean "verify pathname, then delete pathname" capability with an identity-bound destructive primitive.
- A practical cross-platform design is quarantine-before-authorization:
  1. move the candidate atomically to a unique, non-overwriting quarantine name on the same filesystem;
  2. verify the quarantined object against the scanned size/fingerprint after acquisition;
  3. verify that another current group member remains a valid survivor;
  4. only then recycle/delete the quarantined object;
  5. if candidate validation or survivor validation fails, restore the quarantined object to its original name when safely possible, otherwise retain it under quarantine and report a recovery-required failure instead of deleting it.
- Prefer an object/handle identity binding on Windows if implemented cleanly; do not declare this fixed by merely adding another lstat/stat/hash immediately before the existing pathname-based SHFileOperationW call.
- Quarantine destination must be collision-proof and must never overwrite another file.
- Preserve T-45 semantics: a failed deletion remains a valid on-disk survivor and remains armed/present.
- Preserve logging truthfulness and only disarm a row after the exact verified object has actually been removed/recycled.

VERIFY:
- Add a regression that changes/replaces the selected original pathname AFTER its last ordinary verification but BEFORE destructive use; the replacement must remain untouched.
- Add a regression where the acquired/quarantined object fails fingerprint validation; it must not be deleted.
- Add a regression where the survivor vanishes after candidate acquisition; candidate must be restored/retained, not destroyed.
