--------------------------------------------------
P0-A: T-61 REINTRODUCES PATH-BASED TOCTOU
--------------------------------------------------

File: delete_duplicates_gui.py
Symbols:
- acquire_candidate()
- restore_candidate()
- send_to_trash()
- _execute_destructive_batch()

Relevant lines: 193-245, 1641-1675.

ROOT CAUSE
T-49 originally moved the scanned candidate to a
quarantine pathname and performed destructive work
against that acquired pathname.

T-61 restores the acquired file to its original path
before calling the destructive OS operation.

That creates a new window between restoring the
pathname and opening/deleting its current occupant.

The application's cooperative destructive_lock does
not prevent unrelated filesystem processes from
replacing that pathname.

DETERMINISTIC REPRODUCTION
1. Create an ordinary scanned duplicate in a temp dir.
2. Acquire it under a unique quarantine pathname.
3. Invoke production send_to_trash(qpath,
   original_path=original).
4. At the destructive OS call boundary, after
   restoration but before deletion:
   - move the acquired original elsewhere;
   - create a different, previously unscanned file
     at the original pathname.
5. Let the destructive operation continue.

OBSERVED
The unscanned replacement is deleted.
The previously scanned object remains elsewhere.
The quarantine pathname no longer exists.

REQUIRED CORRECTION
Restore object-identity-bound destructive semantics.

The object actually recycled must be exactly the
verified acquired object.

Do not treat "restore immediately before delete"
as an atomic operation.

Investigate the proper Windows API and file-handle
ownership contract.

If original-name restoration cannot be guaranteed
without reopening a pathname race:
- preserve the safe quarantine-based deletion;
- create durable original-path/name recovery metadata;
- offer an explicit verified restore workflow;
- never sacrifice object safety for Recycle Bin naming.

Regression requirements:
- deterministic replacement after restoration;
- replacement survives;
- original acquired object identity is preserved;
- occupied destination refuses safely;
- rollback and crash recovery;
- real Windows Recycle Bin acceptance;
- no orphan quarantine files without recovery evidence.

P0-B: T-54 CACHED KEEPER BYPASSES CONTENT VALIDITY
--------------------------------------------------

File: delete_duplicates_gui.py
Symbol: _GroupDeletionState.get_survivor()
Relevant lines: 925-949, 1617-1667.

ROOT CAUSE
A keeper initially passes full fingerprint validation.

Subsequent checks return that cached keeper when
size, mtime_ns and inode are unchanged.

These metadata fields do not prove content identity.

A different file content can retain identical size,
mtime_ns and inode.

DETERMINISTIC REPRODUCTION
1. Create a.bin, b.bin and c.bin with identical data.
2. Select a.bin and b.bin for deletion.
3. Use c.bin as the unselected keeper.
4. Delete a.bin through the production batch.
5. Replace c.bin's content with different bytes
   of the same length.
6. Restore c.bin's previous mtime_ns.
7. Continue the batch with b.bin.

OBSERVED
- c.bin fails full SHA-256 verification.
- Cached stat fields remain unchanged.
- get_survivor() still accepts c.bin.
- Production _execute_destructive_batch() reports
  two successful deletions.
- Zero files with the original fingerprint remain.

REQUIRED CORRECTION
A keeper must never be accepted as a content-valid
copy merely because cached filesystem metadata
matches.

Review the batching architecture.

Prefer a sound identity/content contract over a
fallback that merely adds another metadata check.

Potential approaches:
- fresh content verification at the destructive
  boundary, with measured I/O cost;
- a properly protected object handle with proven
  cross-platform ownership semantics;
- a redesigned batch strategy maintaining a
  demonstrably valid surviving copy.

Do not reintroduce quadratic member traversal.
Do not weaken SHA-256 authorization for performance.

Regression requirements:
- keeper content changes with unchanged size;
- unchanged mtime_ns;
- unchanged inode where supported;
- a valid copy is always retained or deletion refused;
- production batch integration, not only helper tests;
- 1k/2k/4k member performance measurements.
